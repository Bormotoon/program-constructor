## 1. Что это за проект

Открытый аналог [конструктора рабочих программ](https://workprogram.edsoo.ru/)
Института стратегии развития образования. Учитель собирает рабочую программу по
учебному предмету на основе действующих федеральных рабочих программ (ФРП) и
выгружает её в DOCX, ODT, PDF, TXT или Markdown.

**Ключевое отличие от оригинала: нет серверной части.** Оригинал — это сервер с
базой, куда данные ФРП кто-то однажды завёл руками, и учётные записи. Здесь
данные извлечены из официальных PDF заранее и лежат в репозитории, а приложение
целиком работает в браузере.

### Предметная область в двух абзацах

Рабочая программа — обязательный документ учителя на учебный год. Её структура
задана ФГОС: титульный лист, пояснительная записка, содержание обучения,
планируемые результаты (личностные, метапредметные, предметные), тематическое
планирование и поурочное планирование.

Министерство просвещения публикует **федеральные рабочие программы** — эталонные
тексты по каждому предмету. Школьная рабочая программа составляется на их
основе, и большая часть содержания просто переносится из ФРП дословно. Поэтому
задача конструктора — не «сгенерировать текст», а **достать официальный текст и
дать его отредактировать**.

### Масштаб

| Показатель | Значение |
|---|---|
| Исходных ФРП (PDF) | 65 |
| Предметов в каталоге | 74 |
| Уникальных названий предметов | 33 |
| Классов (предмет × год обучения) | 213 |
| Тем тематического планирования | 3 378 |
| Уроков, извлечённых из ФРП | 5 859 |

**Соотношение 3 150 / 5 750 говорит главное о проекте: это задача извлечения
данных, а не задача интерфейса.** Самый сложный файл — не `App.tsx`, а
`tools/frp_parser.py`.

## 2. Быстрый старт

### Запустить приложение

```bash
npm install
npm run dev          # http://localhost:3000
```

Данные ФРП уже лежат в `src/data/frp/` — конвейер разбора запускать не нужно.

### Прогнать все проверки

```bash
npm run lint            # типы
npm run frp:check       # корпус данных
npm run verify:export   # пять форматов выгрузки
npm run verify:import   # импорт КТП во всех кодировках
npm run ui:check        # сценарий в настоящем Chrome
npm run ui:contrast     # контраст палитры по WCAG
```

Ожидаемо: везде код возврата 0. `frp:check` печатает 10 предупреждений — это
[дефекты официальных PDF](#дефекты-официальных-фрп), не ошибки.

### Окружение

| Что | Версия при разработке | Зачем |
|---|---|---|
| Node | 25.2.1 | сборка, проверки |
| Python | 3.14 (venv в `.venv/`) | конвейер разбора |
| `pdfplumber` | 0.11.10 | таблицы из PDF |
| `fonttools` | 4.63.0 | подмножество шрифта для PDF |
| `pdftotext` (poppler) | 24.02 | текстовые разделы из PDF |
| Google Chrome | системный | `ui:check` через playwright-core |
| LibreOffice | опционально | ручная проверка ODT |

Python-окружение:

```bash
python3 -m venv .venv
.venv/bin/pip install pdfplumber fonttools brotli
```

`playwright-core` использует **системный** Chrome (`/usr/bin/google-chrome`),
браузеры не скачиваются. Путь переопределяется переменной `CHROME_PATH`.

## 4. Принципиальные решения

Каждое решение здесь — ответ на конкретную проблему. Если будете их менять,
имейте в виду, от чего отказываетесь.

### 4.1. Данные извлекаются заранее и коммитятся

**Альтернатива:** разбирать PDF на лету или держать данные на сервере.

**Почему так:** разбор одной ФРП занимает минуты, всего корпуса — больше часа.
Это невозможно делать в браузере и незачем делать на сервере. Раз данные
меняются раз в год, их место — в репозитории.

**Следствие:** нет сервера, нет регистрации, нет расходов на инфраструктуру.
Приложение — статические файлы.

### 4.2. Проверка разбора — сверка с самим документом

**Проблема:** как убедиться, что 3 378 тем разобраны правильно? Эталона нет,
глазами не проверить.

**Решение:** в ФРП есть строки «Итого по разделу N» и «ОБЩЕЕ КОЛИЧЕСТВО N». Если
сумма разобранных часов с ними не сходится — разбор неверен. Это единственная
надёжная валидация парсера, и на ней найдено большинство ошибок.

### 4.3. Ошибка разбора ≠ дефект источника

**Проблема:** часть расхождений — арифметические ошибки в самих официальных PDF.
Пока их не отделили, они постоянно числились нашими ошибками и мешали видеть
настоящие.

**Решение:** классификация вынесена в `tools/frp_verify.py`, ею пользуются и
разбор, и проверка корпуса. Признак дефекта источника: сумма объявленных итогов
разделов сходится с итогом класса, **либо** номера тем идут сплошь без пропусков
— значит ни одна строка не потеряна.

**Следствие:** `verified` в каталоге означает «наш разбор сошёлся», а дефекты
документа лежат отдельно в `sourceIssues` с указанием класса.

### 4.4. Состав документа описан один раз

**Проблема:** пять форматов выгрузки. Если каждый знает состав разделов сам, они
разъедутся при первой же правке.

**Решение:** `src/utils/programOutline.ts` описывает документ в
формато-независимых блоках. Форматы только отрисовывают их. Проверка берёт
заголовки из той же модели и сверяет, что каждый дошёл до каждого формата.

### 4.5. Всё тяжёлое грузится по требованию

Стартовый бандл — 74 КБ в brotli (90 КБ в gzip). Библиотеки выгрузки, парсер
Excel и планы предметов вынесены в отдельные чанки.

### 4.6. Хранение — localStorage, перенос — файлами

Нет сервера, значит нет и синхронизации. Программы лежат в браузере, а
переносятся файлами: одна отдельно, все разом резервной копией.

## 5. Конвейер разбора ФРП

```
edsoo/wp-content/uploads/2025/07/*.pdf   (65 файлов)
   │
   ├── frp_parser.py    ──► build/frp/*.json           таблицы планирования  (~1 ч)
   ├── frp_content.py   ──► build/frp-content/*.json   тексты разделов       (~3 мин)
   ├── frp_lessons.py   ──► build/frp-lessons/*.json   поурочные планы       (~30 мин)
   │
   └── build_frp_data.py ─► src/data/frp/*.json + catalog.ts
                             │
                             └─ check_frp_data.py
```

Три прохода независимы и пишут результат на диск отдельно. Это не эстетика:
полный разбор таблиц идёт больше часа и должен переживать прерывание
(`npm run frp:parse` возобновляемый — уже разобранные файлы пропускаются).

Полный прогон:

```bash
npm run frp:parse      # десятки минут, возобновляемо
npm run frp:content
npm run frp:lessons
npm run frp:reparse    # переразбор файлов, где разбор дал сбой
npm run frp:build
npm run frp:check
```

### 5.1. `frp_parser.py` — таблицы планирования

Самая сложная часть проекта. Тематическое планирование — таблица на пять колонок
на десятки страниц:

```
№ п/п │ Наименование разделов и тем │ Количество часов │ Программное содержание │ Основные виды деятельности
```

**Почему `pdfplumber`, а не координаты слов.** Первая версия восстанавливала
таблицу по x-координатам слов — не сработало: границы колонок плывут от страницы
к странице и различаются даже между классами одного документа. Но это настоящие
таблицы Word с линиями разметки, и `pdfplumber` режет ячейки по линиям.

**Ключевые сложности** (каждая — реальный баг, найденный по расхождению часов):

| Проблема | Решение | Что было без него |
|---|---|---|
| Число колонок непостоянно (5 или 7 из-за разрезанных ячеек) | Колонка часов определяется по содержимому — где чаще целые числа | Часы уезжали в текст |
| Объединённые ячейки Word | Колонка часов ищется **в каждой строке отдельно** | Часы терялись в соседних строках одной таблицы |
| Простая нумерация разделов («3», не «3.1») | Колонка часов не может быть крайней | За часы принимался номер раздела |
| Сноски мелким кеглем | Символы ниже `median_size × 0.82` отбрасываются | «165¹» читалось как «1651» |
| Дробные часы «6/10» (базовый/углублённый) | `RE_HOURS`, выбор половины по уровню документа | Колонка часов не находилась, предмет выпадал |
| Разреженные страницы | Двухпроходный разбор: `probe_layout` голосует по всему блоку | Углублённая химия давала 0 классов |
| Мусор перед «Итого» («.Итого по разделу») | Шаблоны допускают короткий небуквенный префикс | Английский СОО: 177 ч вместо 170 |
| Итог без слова «ОБЩЕЕ» | Шаблон принимает «КОЛИЧЕСТВО ЧАСОВ» | История СОО: 136 ч вместо 68 |
| Обрывок текста в колонке «№» | Ловится по нумерации: `2.1` → `2.2` не может начинать раздел | Испанский НОО: раздел рвался пополам |
| Одна таблица на два года (ОБЗР) | Делится по годам при точном совпадении границ разделов | 9 класс не существовал вовсе |
| Потерянная ячейка часов | Если объявлен итог раздела и без часов ровно одна тема — восстанавливается вычитанием | Расхождение в часах |

**Формат выхода** (`build/frp/<pdf-stem>.json`):

```jsonc
{
  "source": "2025_ooo_frp_biologiya_5-9_baza.pdf",
  "subject": "БИОЛОГИЯ", "level": "ООО", "variant": "базовый",
  "grades": [5, 6, 7, 8, 9],
  "courses": [{                    // сборники дают несколько курсов
    "name": "",                    // пусто у обычных программ
    "pages": [120, 180],
    "classes": [{
      "grade": 5,
      "declaredTotal": 34,         // из строки «ОБЩЕЕ КОЛИЧЕСТВО»
      "computedTotal": 34,         // сумма разобранных тем
      "modular": false,
      "notes": [],
      "sections": [{
        "name": "Биология — наука о живой природе",
        "course": "",
        "declaredTotal": 5,        // из строки «Итого по разделу»
        "computedTotal": 5,
        "topics": [{ "num": "1.1", "name": "…", "hours": 2,
                     "content": "…", "activity": "…" }]
      }]
    }]
  }],
  "problems": [],                  // ошибки разбора
  "sourceProblems": []             // дефекты самого PDF
}
```

### 5.2. `frp_content.py` — текстовые разделы

Пояснительная записка, содержание обучения, три группы планируемых результатов.
Отдельный проход: текст без таблиц берётся быстрым `pdftotext -layout`.

**Границы блоков.** Границей служит **любой следующий заголовок верхнего
уровня** (`RE_ANY_HEAD`). Без этого у сборников курсов «предметные результаты»
математики вбирали пояснительную записку и содержание следующего курса — блок
начинался словами «Натуральные числа и нуль».

**Привязка блоков к курсам — по порядку следования**, а не по близости: записка
курса стоит *перед* его содержанием, а результаты — после, и одно правило на оба
случая сдвигало записки на курс назад. Реализация — `pair_with_courses()`.

**Разбивка результатов по классам.** Оборот у разных ФРП свой: «К концу обучения
в 1 классе обучающийся научится» у русского языка, «Предметные результаты
освоения программы по биологии к концу обучения в 5 классе» у биологии. Ловится
одним шаблоном `RE_RESULTS_CLASS`; где разметки нет — текст один на весь уровень
образования и лежит под пустым ключом. Разбито у 52 предметов из 74.

**Отсечение таблиц.** Пояснительная записка истории заканчивается таблицей
распределения курсов, и в текстовом виде она разваливается. `drop_trailing_table()`
отрезает хвост из строк с широкими пробельными разрывами. Затрагивает 2 файла
из 65.

**Формат выхода** (`build/frp-content/<pdf-stem>.json`):

```jsonc
{
  "source": "2025_ooo_frp_matematika-5-9_baza.pdf",
  "notes":   { "": "общая записка", "Алгебра": "…", "Геометрия": "…" },
  "results": {
    "personal": { "": "…" },       // общие на весь предмет
    "meta":     { "": "…" },
    "subject":  { "Алгебра": { "7": "…", "8": "…" } }   // курс → класс → текст
  },
  "courses": { "Алгебра": { "7": "содержание обучения…" } }
}
```

### 5.3. `frp_lessons.py` — поурочное планирование

Есть только у 14 программ из 65.

Два неочевидных места:

- **Строка-диапазон** «Уроки 69–102 | История нашего края | 34» — так ФРП
  оставляет школе часы на региональное содержание. Разворачивается в отдельные
  уроки: школа заполняет их своим содержимым, и в редакторе нужны строки, а не
  одна ячейка. Без этого история 5 класса давала 68 уроков при объявленных 102.
- **Смысл числовой колонки** берётся из шапки таблицы: у русского языка это
  «часы на практические работы», у истории — «Количество часов. Всего», где у
  каждого урока стоит единица. Без различения все 408 уроков истории уезжали
  в графу практикума, и в выгрузке набегало 102 часа практических на класс.

**Варианты планирования.** ФРП иногда предлагает несколько: под конкретный
учебник и для самостоятельного конструирования (окружающий мир), разная
недельная нагрузка (русский язык 6 класса). Все сохраняются, выбор — за
учителем.

### 5.4. `build_frp_data.py` — сборка данных приложения

- **65 PDF → 74 предмета.** Сборники разделяются: «Математика 5–9» содержит
  алгебру, геометрию и вероятность со статистикой, и школы пишут по ним
  отдельные программы.
- Один файл на предмет плюс `catalog.ts` со списком и ленивыми загрузчиками.
- **Норма часов** берётся из объявленной в ФРП строки (`declaredHours`), а не
  из суммы разобранного: она авторитетна и не зависит от полноты разбора.
- Повторные блоки «Тематическое планирование» (у физкультуры он есть дважды)
  отсеиваются по числу тем.

### 5.5. `check_frp_data.py` — проверка корпуса

Что проверяется:

- сходимость часов — через `frp_verify.verify()`, тем же кодом, что и разбор;
- непустые названия тем, отсутствие «класса 0», допустимые номера классов;
- правдоподобная годовая нагрузка (16…250 часов);
- иероглифы в тексте (признак повреждения; у китайского языка разрешены);
- совпадение каталога с файлами планов, отсутствие сирот и дублей slug;
- нумерация уроков подряд с единицы;
- число уроков против годовой нормы — но только если **ни один** вариант
  планирования в норму не укладывается.

### 5.6. `reparse_stale.py` — переразбор

Отбирает файлы **по содержимому**, а не по времени изменения: длинный прогон
держит в памяти ту версию парсера, с которой стартовал, и свежая отметка времени
у JSON ничего не гарантирует. Выводы считаются заново через `frp_verify`, а не
читаются из поля `problems` — его тоже записал старый код.

## 6. Модель данных

### 6.1. Программа учителя

`src/data/program.ts`:

```ts
interface ProgramData {
  // титульный лист
  regionalAuthority, founder, schoolName, locality, year: string;
  approvals: ApprovalKind[];        // 'reviewed' | 'agreed' | 'approved'
  reviewedBy, agreedBy, approvedBy: string;

  // предмет
  frpSlug: string;                  // ключ записи каталога; пусто — заполнено вручную
  subject, variant, grade, teacherName, academicYear: string;
  educationLevel: 'НОО' | 'ООО' | 'СОО';

  // текстовые разделы
  normativeBase: string;            // пояснительная записка целиком
  subjectContent, personalResults, metaResults, subjectResults: string;
  methodologicalSupport: string;

  // таблицы
  thematicPlan: PlanSection[];      // { id, name, topics: PlanTopic[] }
  lessonPlan: LessonRow[];          // { id, number, topic, hours, control, practice, date }
}
```

`normalizeProgram(parsed)` приводит любой разобранный JSON к этой модели: добирает
недостающие поля из умолчаний и чинит списки, оказавшиеся не списками. **Одна
функция на все источники** — хранилище браузера, файл программы, резервная копия.

### 6.2. Данные ФРП

`src/data/frp/catalog.ts` (генерируется):

```ts
interface FrpCatalogEntry {
  slug: string;                     // ключ файла плана
  subject, variant: string;
  level: FrpLevel;
  grades: number[];
  hoursByGrade: Record<string, number>;   // годовая НОРМА, не сумма таблицы
  totalHours: number;
  modular: boolean;                 // ФРП перечисляет модули на выбор
  hasLessons: boolean;              // в ФРП есть поурочное планирование
  source: string;                   // имя исходного PDF
  verified: boolean;                // наш разбор сошёлся
  sourceIssues: FrpSourceIssue[];   // дефекты самого PDF, { grade, text }
  topicCount: number;
}
```

`FrpPlan` (файл предмета) содержит `note`, `personalResults`, `metaResults`,
`subjectResults: Record<grade, string>` и массив `classes`. Предметные результаты
лежат на уровне плана, а не класса: у истории это 28 тысяч знаков, и в каждом из
пяти классов лежал бы один и тот же текст.

Загрузка — только ленивая:

```ts
const plan = await loadFrpPlan(slug);   // динамический import()
```

### 6.3. Библиотека программ

`src/data/library.ts`, ключи в `localStorage`:

```
fgos-library-index    → LibraryEntry[]  { id, title, subject, grade, level, updatedAt, size, renamed? }
fgos-program:<id>     → ProgramData
fgos-library-current  → id открытой программы
```

Список хранится **отдельно** от содержимого: чтобы показать перечень из десяти
названий, иначе пришлось бы разобрать пару мегабайт JSON.

`fgos-program-data-v3` — старый ключ на одну программу. `migrateSingleProgram()`
переносит его в библиотеку при первом запуске и удаляет.

### 6.4. Файлы обмена

| Формат | Поле `format` | Что внутри |
|---|---|---|
| Одна программа | `fgos-program` | `{ format, version, savedAt, program }` |
| Резервная копия | `fgos-library` | `{ format, version, savedAt, programs: [{title, program}] }` |

`version` = 1. Файл более новой версии отвергается с внятным сообщением.

## 7. Приложение

### 7.1. Состояние

Всё в `App.tsx`, обычный `useState`. Ни Redux, ни контекста — одна форма, одна
открытая программа. Ключевые единицы состояния:

```ts
programId      // id открытой программы в библиотеке
data           // ProgramData — то, что редактируется
entries        // список библиотеки для диалога
plan           // FrpPlan выбранного предмета, грузится лениво
pendingFill    // slug, для которого ждём план, чтобы подставить тексты ФРП
storageError   // место в браузере кончилось
activeTab      // вкладка, включая 'preview'
```

### 7.2. Три места, требующие внимания

**Инициализация — одной функцией.** `openInitialProgram()` разрешает
идентификатор и данные вместе. Если разрешать их порознь двумя инициализаторами
`useState`, они могут разойтись — программа взята одна, данные прочитаны от
другой, и первое же автосохранение затрёт чужую программу.

**Асинхронное предзаполнение.** Тексты ФРП лежат в файле плана, который грузится
по выбору предмета. Флаг `pendingFill` говорит эффекту загрузки подставить их,
когда план придёт. Восстановление сохранённой программы флага не ставит — иначе
загрузка плана затирала бы написанное учителем.

**Стабильные обработчики.** В поурочном плане бывает 200 строк. Строки
мемоизированы, ссылки на обработчики стабильны (`useCallback` от `patch`), иначе
каждое нажатие клавиши перерисовывало бы всю таблицу. Замеряется в `ui:check`:
**57–79 мс** на ввод в таблице из 103 строк.

### 7.3. Автосохранение

Дебаунс 500 мс, запись в библиотеку. При `QuotaExceededError` показывается полоса
с кнопкой «Сохранить в файл» — молча терять работу нельзя.

### 7.4. Тексты следуют за классом

Содержание обучения и предметные результаты у каждого класса свои. При смене
класса обновляются — но **только если совпадают с текстом ФРП прежнего класса**,
то есть учитель их не правил. Правку узнаём сравнением, а не флагом.

### 7.5. Оформление

`src/index.css` — семантические токены в oklch (`--color-ink`, `--color-brand`,
`--color-danger` и т. д.). Тёмная тема описана **отдельными значениями токенов**,
а не инверсией светлых. Контраст считается по формуле WCAG из самих токенов
(`npm run ui:contrast`), а не оценивается на глаз.

Доступность: видимое кольцо фокуса (`focus-visible`, `focus:outline-none` без
замены не используется нигде), подписи у всех полей и кнопок-иконок, управление
списком подсказок стрелками, ссылка «Перейти к содержимому»,
`prefers-reduced-motion`.

### 7.6. Связка с каталогом перечня учебников

Раздел «УМК и обеспечение» — единственный, для которого ФРП не даёт готового
текста: подставляется болванка, а конкретные учебники учитель писал руками.
Если рядом на том же домене развёрнут каталог ФПУ, между ними ходят в обе
стороны — `src/utils/fpuHandoff.ts` и `src/components/UmkFromCatalog.tsx`.

**Почему через `localStorage`, а не запросом.** Сервера нет ни у конструктора,
ни у каталога, зато домен общий. Каталог кладёт список в ключ
`fpu-umk-handoff` и открывает конструктор ссылкой с `#umk`; конструктор по
этому хешу сразу открывает нужную вкладку. Обмен не выходит за пределы
браузера, и утверждение «наружу ничего не уходит» остаётся верным.

**Почему список ловится без перезагрузки.** Каталог обычно открыт в соседней
вкладке, поэтому слушаются два события: `storage` — запись пришла из другой
вкладки того же origin, `focus` — учитель вернулся сюда. Одного `storage` мало:
он не приходит во вкладку, которая сама сделала запись, и не срабатывает, если
каталог открывали до конструктора.

**Почему предмет уходит поиском, а не точным фильтром.** Названия в ФРП и ФПУ
совпадают не всегда: «Труд (технология)», «Иностранный (английский) язык».
`catalogUrl` вырезает скобочные уточнения и передаёт остаток как `q=` —
точный `subjects=` дал бы пустую выдачу.

**Что защищает от мусора.** `readHandoff` проверяет формат (`format:
'fpu-umk'`, непустой текст, массив книг) и возраст: непринятая передача живёт
сутки. Испорченный, чужой или устаревший ключ удаляется молча — это фоновая
проверка при каждом заходе на раздел, а не действие учителя, о котором надо
отчитываться.

**Чего здесь намеренно нет.** Список не вставляется сам: показывается, что
пришло (сколько учебников, предметы, классы, первые четыре названия), и учитель
выбирает — вставить, дописать в конец или отклонить. Молчаливая подмена
набранного руками текста была бы худшим поведением из возможных.

**Оговорка при развёртывании.** Каталог ищется по относительному пути `../fpu/`.
На GitHub Pages соседа нет, и кнопка ведёт на 404 — связка работает там, где
оба приложения стоят рядом на одном домене.

## 8. Выгрузка документа

### 8.1. Общая модель

`src/utils/programOutline.ts` описывает документ блоками:

```ts
type OutlineBlock =
  | { kind: 'cover';   text, bold?, small? }   // строка титульного листа
  | { kind: 'approvals'; items: {label, text}[] }
  | { kind: 'space';   size: 'small' | 'large' }
  | { kind: 'pagebreak' }
  | { kind: 'heading';    text }               // раздел; начинает новую страницу
  | { kind: 'subheading'; text }
  | { kind: 'body';       text }               // абзацы через \n
  | { kind: 'table';      table: OutlineTable }
```

`buildOutline(data)` строит состав и порядок разделов **один раз**. Пять форматов
только отрисовывают блоки.

**Ширины колонок тоже здесь** — это свойство документа, а не формата. Подобраны
по метрикам Times New Roman в 10 pt: колонке часов нужно 0,14 ширины, потому что
слово «Количество» занимает 18,9 мм плюс поля ячейки. При 0,08 редактор ломал его
как «Коли/честв/о».

### 8.2. Пять форматов

| Формат | Реализация | Чанк (gzip) | Особенности |
|---|---|---|---|
| DOCX | библиотека `docx` | 103 КБ | шапка таблицы 10 pt, тело 12 pt |
| ODT | вручную: zip с XML через `fflate` | **2,7 КБ** | `mimetype` первым и без сжатия |
| PDF | `jsPDF` + `jspdf-autotable` | 204 КБ | встроенный шрифт, ручная выключка строк |
| TXT | строки | 1,2 КБ | таблицы как «поле: значение» с переносом |
| Markdown | строки | (тот же чанк) | настоящие таблицы, BOM для Windows |

**PDF — единственный по-настоящему трудный.** Стандартные шрифты PDF не содержат
кириллицы, поэтому шрифт встраивается: Liberation Serif, метрически совместимый
с Times New Roman, под SIL OFL 1.1. Целиком три начертания весят 1,1 МБ —
`tools/build_pdf_fonts.py` оставляет только нужные символы, получается **173 КБ**.

Выключку строк по ширине пришлось написать вручную (`justifyLine`): встроенная
в jsPDF работает только на массиве строк, который он разбил сам, и не сочетается
с красной строкой — все строки массива он рисует от одного левого края.

**ODT оказался дешевле всех.** Это zip с несколькими XML, и генератора, который
стоило бы тащить в бандл, нет. Требования формата: `mimetype` лежит первым и без
сжатия (по нему формат опознают до распаковки), объединённые ячейки занимают своё
место `<table:covered-table-cell/>`.

### 8.3. Печать

Отдельный путь: предпросмотр свёрстан как документ (Times New Roman, A4), а
интерфейс скрыт `print:hidden`. `ui:check` печатает программу в PDF и проверяет,
что он получился многостраничным.

## 9. Проверки

| Команда | Что делает | Объём |
|---|---|---|
| `npm run lint` | `tsc --noEmit` | — |
| `npm run frp:check` | сходимость часов, целостность каталога | 65 файлов |
| `npm run verify:export` | данные → планы → пять форматов | 42 проверки |
| `npm run verify:import` | файл → колонки → разделы плана | 7 файлов, 71 проверка |
| `npm run ui:check` | сценарий учителя в настоящем Chrome | 48 проверок |
| `npm run ui:contrast` | контраст по WCAG из токенов | обе темы |

### Два принципа, которые себя оправдали

**Проверять там, где ломается.** Выгрузка проверяется скачиванием файла в живом
браузере — сломанный ленивый импорт не виден ни сборке, ни типам. Импорт КТП
проверяется настоящими байтами в cp1251, а не строкой в UTF-8: разница между
ними и была багом (#12), и всякая проверка, которая берёт уже декодированный
текст, его пропускает. Сохранность
программ проверяется тем же способом, каким работу теряют на практике: завести
вторую программу, переключиться на первую, перезагрузить страницу.

**Не проверять себя своим же кодом.** Прежняя проверка DOCX искала подстроку в
сыром буфере zip — то есть **не заметила бы пропажу ни одного раздела**, потому
что содержимое сжато. Теперь запись распаковывается (`readZipEntry`), а заголовки
разделов берутся из общей модели, а не переписываются в проверке.

### Что покрывает `ui:check`

Выбор предмета → подстановка текстов ФРП → заполнение тематического плана →
ленивый чанк Excel → разворачивание поурочного плана → отклик ввода →
предпросмотр → печать в PDF → скачивание всех пяти форматов → библиотека
(создание, переключение, перезагрузка, резервная копия) → отсутствие
горизонтальной прокрутки на 375 px. Всё в светлой и тёмной темах, с проверкой
консоли на ошибки.

Скриншоты складываются в `build/ui/`.

## 10. Развёртывание

**Серверная часть не нужна.** `npm run build` даёт `dist/` — статические файлы.

### Что реально скачивает пользователь

| Что | Когда | brotli |
|---|---|---|
| `index.html` + `main.js` + `main.css` | всегда | **83 КБ** |
| Шрифт Inter (кириллица + латиница) | всегда | ~65 КБ |
| Чанк предмета | при выборе предмета | медиана 36 КБ, максимум 168 |
| Библиотека DOCX | по нажатию | 103 КБ |
| Библиотека PDF со шрифтом | по нажатию | 204 КБ |

**Типичный сеанс — около 290 КБ.** Повторный визит — почти ноль: у файлов хеш в
имени, браузер отдаёт их из кеша.

`dist/` целиком — 24 МБ, но столько скачает лишь тот, кто откроет все 74 предмета.

### Нагрузка

**Процессор и память сервера — ноль.** Никакого кода приложения сервер не
исполняет: nginx отдаёт файл с диска. Разбор данных, генерация DOCX, вёрстка PDF
— всё в браузере учителя.

Остаётся трафик, линейный по числу пользователей:

| Учителей в день (первый визит) | Трафик |
|---|---|
| 1 000 | ~290 МБ |
| 10 000 | ~2,9 ГБ |
| 100 000 | ~29 ГБ |

Десять тысяч учителей в день — нагрузка уровня личного блога.

### Что настроить

1. **Предварительное сжатие.** Vite его не делает. `main.js`: 302 КБ без сжатия,
   87 КБ в gzip, 74 КБ в brotli. Либо `gzip on`, либо заранее сжатые файлы плюс
   `gzip_static`/`brotli_static`.
2. **Кеширование.** Файлы в `assets/` имеют хеш в имени —
   `Cache-Control: public, max-age=31536000, immutable`. `index.html` — наоборот,
   `no-cache`.
3. **Больше ничего.** Роутера нет, правила фолбэка не нужны. HTTPS функционально
   не требуется: `localStorage` и скачивание работают и по http.

**Обязательное требование:** это должен быть HTTP-сервер. Открыть
`dist/index.html` двойным щелчком не выйдет — ES-модули и динамический импорт
блокируются на `file://`.

Подойдёт: nginx, Caddy, GitHub Pages, Cloudflare Pages, S3+CDN, сервер внутри
школьной сети без интернета.

**Конвейер разбора в продакшене не участвует.** Час на разбор и требовательность
к памяти — разовая операция на машине разработчика; на сервер попадают готовые
JSON.

## 11. Известные ограничения

### Дефекты официальных ФРП

Семь программ, где перечень тем не сходится с итогом, объявленным в том же
документе. Установлены сверкой с исходным текстом, исправить нельзя. Приложение
предупреждает о них по выбранному классу.

| Программа | Что в документе |
|---|---|
| История ООО, 5 класс | «Итого по разделу 33» при темах на 22 ч; при этом 6+22+20+20 = 68 совпадает с «Общим количеством часов по курсу» |
| История СОО, 11 класс | раздел «СССР в 1945–1991 гг.»: итого 27 при темах 1.1–1.6 на 4+7+8+5+1+1 = 26 |
| Литература ООО, 7 класс | раздел объявляет 5 ч, перечислены три темы на 1+1+2 |
| Английский НОО, 4 класс | две строки с номером «3.8»; темы дают 21 ч при объявленных 23 |
| Музыка НОО, 4 класс | темы по модулям дают 33 ч при объявленных 34 |
| Труд НОО, 4 класс | девять тем на 34 ч плюс «Подготовка портфолио — 1 ч», объявлено 34 |
| Немецкий СОО, 10 и 11 классы | темы дают 102 ч при объявленных 105 |

### Не поддерживается

- **Внеурочная деятельность.** В зеркале одна готовая программа — для корпуса
  мало. Структура близка к предметной, но заголовки другие («СОДЕРЖАНИЕ КУРСА
  ВНЕУРОЧНОЙ ДЕЯТЕЛЬНОСТИ», «Наименование модулей и тем курса»), поэтому
  конвейер её не распознаёт. Работы — три-четыре регулярки.
- **Адаптированные программы (ФАООП).** Их текстов в офлайн-копии нет вовсе,
  только методические рекомендации. У них другой состав разделов (коррекционная
  работа), так что это не «ещё 65 PDF в тот же парсер».

### Слабые места

- **Нормативная база** (`src/data/normativeBase.ts`) — номера приказов зашиты
  константами и не самопроверяемы: в корпусе ФРП приказов нет, сверять не с чем.
  Тут уже была ошибка — ФГОС НОО № 280 вместо 286 и ФГОС СОО № 371 вместо 413,
  найдено ручной сверкой.
- **Настоящего офлайна нет.** Service worker отсутствует, чанк предмета
  подгружается по сети при выборе. Уже открытые предметы работают из кеша.
- **OSM Nominatim** — единственный запрос наружу: подсказка при вводе школы шлёт
  набранный текст в OpenStreetMap. Идёт из браузера учителя, с его IP; примерно
  2–5 запросов на программу. Поле подписано, без подсказки всё работает.
- **localStorage ~5 МБ** — около двух десятков программ. Переполнение
  обрабатывается явно, но само ограничение остаётся.

## 12. Подводные камни

То, что легко сломать, не заметив.

### Данные

- **`src/data/frp/**` генерируется.** Правка руками теряется при следующем
  `frp:build`.
- **`hoursByGrade` — это норма, а не сумма таблицы.** У модульных предметов
  (ОРКСЭ, музыка, физкультура, труд) сумма законно больше: ФРП перечисляет все
  модули на выбор. ОРКСЭ даёт шестикратное превышение — шесть модулей по 34 часа
  при норме 34.
- **`verified: false` не значит «плохие данные».** Значит «наш разбор не сошёлся».
  Дефекты источника лежат в `sourceIssues` и на `verified` не влияют.

### Конвейер

- **Не запускать `pkill -f 'frp_parser'`** — шаблон совпадёт с собственной
  оболочкой, и она умрёт (наблюдалось многократно, exit 144). Убивать по PID.
- **Долгий прогон держит старую версию парсера.** Правка `frp_parser.py` во время
  прогона не подхватится. Отбор на переразбор — по содержимому
  (`reparse_stale.py`), не по времени файла.
- **`frp:parse` возобновляемый.** Чтобы переразобрать заново, файл надо удалить.
- **Хост чувствителен к памяти.** Тяжёлые команды запускать с `timeout` и `nice`;
  минифицированные однострочные файлы не обрабатывать через `grep -oE`.

### Приложение

- **Два инициализатора `useState` не должны разрешать одно и то же порознь** —
  см. `openInitialProgram()`. Это уже приводило к риску затирания программы.
- **`focus:outline-none` без замены не использовать** — ломает клавиатурный фокус.
- **Sticky `<thead>` внутри `overflow-x-auto`** перекрывает первую строку. Убрано
  намеренно.
- **Обязательная звёздочка у поля — вне `<label>`**, иначе попадает в доступное
  имя («Предмет*»).

### Выгрузка

- **Состав разделов правится только в `programOutline.ts`.** Добавление раздела
  прямо в `docxExport.ts` разойдётся с остальными четырьмя форматами; проверка
  это поймает, но лучше не делать.
- **Ширины колонок — там же.** Подобраны по метрикам шрифта; произвольные числа
  ломают заголовки посреди слова.
- **`mimetype` в ODT — первым и без сжатия.** Иначе часть редакторов файл не
  опознает.

### Проверки

- **`ui:check` требует свободный порт 4180.** Застрявший `vite preview` от
  прошлого прогона отдаёт старую сборку, и проверка молча тестирует не то.
  Проверять: `ss -ltn | grep 4180`.
- **`tsconfig.json` обязан иметь `include: ["src"]`.** Без него `allowJs`
  затягивает `edsoo/` и `dist/`, и `tsc` падает по памяти при 4 ГБ кучи.

## 13. Рецепты типичных изменений

### Обновить корпус ФРП на новый учебный год

1. Положить новые PDF в `edsoo/wp-content/uploads/<год>/<месяц>/`.
2. Поправить пути в скриптах `frp:*` в `package.json`.
3. `npm run frp:parse && npm run frp:content && npm run frp:lessons`
4. `npm run frp:reparse` — переразбор сбойных.
5. `npm run frp:build && npm run frp:check`
6. Разобраться с каждой ошибкой: это ошибка разбора или дефект PDF? Проверять
   сверкой с исходным текстом через `pdftotext -layout`.
7. Обновить таблицу дефектов в этом документе и в README.

### Добавить шестой формат выгрузки

1. Написать `src/utils/<формат>Export.ts`, потребляющий `buildOutline(data)`.
2. Добавить пункт в `FORMATS` и ветку в `run()` в `ExportMenu.tsx`.
3. Добавить проверки в `tools/verify_export.ts` — включая цикл по заголовкам
   разделов.
4. Добавить формат в список `ui_check.mjs`.
5. Обновить README и раздел 8 этого документа.

### Добавить раздел в документ программы

1. Добавить поле в `ProgramData` и в `defaultProgram`.
2. Добавить блоки в `buildOutline()` — этого достаточно для всех пяти форматов.
3. Добавить вкладку в `TABS` и её разметку в `App.tsx`.
4. Добавить отметку заполненности в объект `done`.
5. Предпросмотр (`ProgramPreview.tsx`) верстается отдельно — обновить и его.

### Поддержать внеурочную деятельность

1. `frp_content.py`: добавить «СОДЕРЖАНИЕ КУРСА ВНЕУРОЧНОЙ ДЕЯТЕЛЬНОСТИ» в
   `RE_START` и «ПЛАНИРУЕМЫЕ РЕЗУЛЬТАТЫ ОСВОЕНИЯ ПРОГРАММЫ КУРСА» в границы.
2. `frp_parser.py`: добавить «Наименование модулей и тем курса» в `RE_TABLE_HEAD`.
3. Титульный лист и выгрузка говорят «учебного предмета» — для курса нужна
   другая формулировка, вероятно поле в `ProgramData`.

### Сделать настоящий офлайн

Добавить service worker, кеширующий `assets/**` по стратегии cache-first
(файлы неизменяемы, у них хеш в имени) и `index.html` по network-first. Плюс
web-манифест. Проверку добавить в `ui_check.mjs`: вторая загрузка с
`context.setOffline(true)`.

## Приложение: происхождение данных

Источник — официальные ФРП 2025 года с [edsoo.ru](https://edsoo.ru), Институт
стратегии развития образования. Офлайн-копия сайта лежит локально в `edsoo/`
(6,3 ГБ) и в репозиторий не входит: версионируется только результат разбора
(`src/data/frp/`), которого приложению достаточно. Скачивать PDF нужно, лишь
если правится сам конвейер. Сами программы:

```
edsoo/wp-content/uploads/2025/07/2025_{noo,ooo,soo}_frp_*.pdf
```

14 файлов НОО, 22 ООО, 29 СОО. Базовый и углублённый уровни — отдельными
файлами. Имена почти единообразны: у одного файла дефис вместо подчёркивания
(`2025_ooo_frp-nemeczkij_5-9.pdf`), поэтому скрипты отбирают файлы шаблоном
`2025_*frp*.pdf`, а не по уровню. По состоянию на июль 2026 более новой редакции ФРП в зеркале нет
(в `uploads/2026/` 116 PDF, среди них ФРП отсутствуют).

Шрифт для PDF — Liberation Serif (© 2012 Red Hat), SIL Open Font License 1.1,
текст лицензии в `src/assets/fonts/LICENSE`.

## Приложение: почему xlsx стоит не из npm

В `package.json` зависимость `xlsx` указана тарболлом
`https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, а не версией из реестра.
Причина не в прихоти: пакет в npm заброшен на 0.18.5, и в нём висят две
неисправленные уязвимости — прототипное загрязнение (до 0.19.3) и ReDoS (до
0.20.2). Свежие сборки SheetJS публикует только на своём CDN, и это его
собственная документированная схема поставки.

Плата за это — `npm ci` ходит не только в реестр npm. Целостность тарболла
зафиксирована в `package-lock.json`, так что подмена на стороне CDN сборку
не пройдёт, но при недоступности cdn.sheetjs.com установка зависимостей
упадёт. Если это когда-нибудь станет проблемой, замена — перейти на
поддерживаемую библиотеку разбора XLSX; сам разбор занимает
`src/components/ExcelImportDialog.tsx` и использует три функции
(`read`, `utils.sheet_to_json`).
